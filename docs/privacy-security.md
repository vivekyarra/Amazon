# Privacy and security

Synthetic fixtures contain no private household conversations, addresses or identities. The optional public video reference is licensed/attributed separately and never labeled consented household footage. Browser clients never receive Bee, Ring or AWS credentials. Every contract, incident, media, TV session and event read is household-scoped.

Authentication uses private bootstrap credentials, memory-only salted scrypt hashes and random 256-bit session tokens. Only SHA-256 token hashes are persisted; sessions expire after eight hours and logout revokes them. Cookies are HttpOnly/SameSite Strict and always Secure in live mode. Live API/MCP access requires HTTPS, configured origins, a provisioned 32-byte owner-only key and owner passwords of at least sixteen characters; a demo administrator is prohibited. Replay mutation routes require the isolated demo administrator. MCP owner-provided utterances remain explicitly labeled as MCP input rather than genuine Bee capture.

Writes require strict request validation and idempotency; conflicting reuse returns 409. Origins, request bounds, login/command rate limits, CSP, no-referrer, no-sniff and no-store are enforced. The application limiter is single-process; a reverse proxy must also enforce connection/body/time limits. AWS backend ingress is limited to the HTTPS ALB, so its forwarded HTTPS headers are trusted only inside that network boundary.

AES-256-GCM encrypts household aggregates, command responses, inbox payloads and artifacts; associated data binds each record to its identity and household. A missing/wrong key or damaged ciphertext fails closed. Keys and bootstrap files have owner-only permissions and remain ignored by git. The local generated key shares a private deployment volume for development; live deployments provision it separately. Existing plaintext ledgers require explicit migration opt-in (`ALLOW_LEGACY_LEDGER_MIGRATION=true`) and disposal of old unencrypted backups. Never opt into migration to bypass a missing key for an encrypted ledger.

Consent is required before compilation/evidence processing. Revocation cancels queued inbox work, pauses watchdogs/workouts and stops live camera sessions. Frame callbacks recheck consent transactionally; the media route immediately refuses revoked access. No browser captures hidden audio/video. There is no biometric identification or automatic accusation. User confirmations retain `USER_CONFIRMED` provenance. Motion notifications, unseen objects and model speech extraction cannot mark a physical contract verified.

Artifacts expire after seven days by default; owners can change this (see "Owner privacy controls"). The worker physically removes expired local bytes and retains hash-chain tombstones. Retrieval/export distinguishes expiration from tampering. Cloud replication preserves ciphertext and adds private SSE-KMS encryption. Immutable retries do not refresh artifact age; the cloud worker deletes all S3 versions of expired media and restore never resurrects them. S3 seven-day lifecycle rules are an eventual backstop, not instantaneous deletion. AWS PITR/retained volumes and operational backups have their own retention policies; transcript/audit metadata is not automatically erased after seven days.

## Owner privacy controls (spec 11.1 PRIVATE_MASKS, 12.1, 12.2, 12.4)

Implemented in `apps/mcp-orchestrator/done_irl/privacy.py` with routes under `/api/privacy` and a compact panel on the console's Connections & privacy page. Every write requires an authenticated session for the caller's own household (`owner`, or the judge administrator for the isolated `demo` household only), an `Idempotency-Key`, strict request validation, and returns a `trace_id`; each change emits an audit event (`privacy.*`) into the encrypted household ledger. Settings are stored inside the household's AES-GCM aggregate, so another household can neither read nor change them.

- **Per-camera exclusion** (`POST /api/privacy/cameras/exclusion`). Only cameras bound to the caller's household (or `synthetic-porch` in replay) can be configured. An excluded camera cannot start a WHEP/camera session (`CAMERA_EXCLUDED`, checked inside the idempotent command before any external call, which also covers the MCP bridge); an open session for that device is stopped immediately and by the worker loop; frame callbacks recheck exclusion transactionally; signed Ring webhooks from the device are acknowledged with `202 {"processed": false}` without storing the payload; already-queued inbox events are cancelled with their payload discarded; synthetic porch scenarios refuse observation and evidence collection. Live studio sessions already require a camera; the replay studio uses synthetic marker frames, not a camera device.
- **PRIVATE_MASKS** (`POST /api/privacy/cameras/masks`). Up to 16 normalized polygons (3–64 points in [0, 1]) per camera with an incrementing `calibration_revision` and optimistic revision checks. Masked pixels are zeroed in frames before detection, before the live relay JPEG and frame hashes, and in stored derived evidence (snapshots, person crops and annotated clips) before encoding, so `sha256_original` covers the masked bytes. Each such evidence record carries a `privacy_mask` entry (camera, calibration revision, region count, scope). **Original artifacts:** the synthetic source clip (`REMOVAL_CLIP_ORIGINAL`) is preserved unmasked, encrypted with AES-256-GCM, as the chain-of-custody original, and its manifest entry says so (`ORIGINAL_UNMASKED_ENCRYPTED`). No live Ring clip is stored today. Masks do not replace a camera's own privacy zones.
- **Retention** (`POST /api/privacy/retention`, 1–30 days). New artifacts record `retention_days_at_capture`. Existing, unexpired artifacts get a new effective `retention_expires_at` computed from their capture time; the at-capture value moves to `retention_expires_at_original`, which the hash-chain verifier uses, so the evidence chain is not rewritten. Shortening retention deletes now-due bytes in the same transaction and keeps tombstones; already-expired artifacts are never resurrected. The cloud worker then deletes all S3 versions using the effective expiry.
- **Provider disconnect** (`POST /api/privacy/providers/{bee|ring}/disconnect`). Records a durable `REVOKED` state, deletes the household's provider cursor, cancels and erases queued inbox payloads, stops the Ring session or the Bee stream and drops the in-process Bee token copy. Integration status shows `NOT_CONNECTED`. Revocation is enforced at enqueue, processing, webhook, camera start and frame callback. Toggling global consent or restarting the service does **not** reconnect (startup honors revocation). Only an explicit owner `.../reauthorize` clears it; Bee streaming then needs a service restart with provisioned credentials. **Limit:** provider credentials are server-provisioned secrets (environment/secret store) and are never stored in the ledger. Disconnect does not revoke tokens upstream at Amazon/Ring and does not erase the operator's secret store; the operator must rotate/remove them there.
- **Household deletion** (`POST /api/privacy/household/delete`) requires `household_id` equal to the caller's own household and the exact phrase `DELETE ALL HOUSEHOLD DATA`. In one transaction it deletes that household's contracts, events, alerts, incidents, subagents, schedules, evidence bytes and tombstones, inbox receipts, provider cursors, cached command responses and pending cloud outbox snapshots. It then disables consent, stops the camera session and checkpoints the WAL. Other households are untouched. It keeps a minimal receipt (ID, timestamp, per-type counts, cloud status) and only non-content safety settings (camera exclusions, provider revocations, retention days) so deletion never re-enables collection; masks (home layout) are deleted. With AWS enabled, a `cloud_deletions` job erases every S3 object version under `<household>/`, every DynamoDB item under `HOUSE#<household>` and the household's EventBridge schedules. This runs before any newer snapshot is republished, and a failure blocks the republish and retries. **Not covered:** EBS/SQLite operator backups, DynamoDB PITR history, CloudWatch logs and data held by providers follow their own retention.

Tests: `apps/mcp-orchestrator/tests/test_privacy.py` (`test_privacy_controls_require_authenticated_owner_and_idempotency`, `test_camera_exclusion_blocks_synthetic_collection_and_is_audited`, `test_live_excluded_camera_cannot_start_and_webhook_is_acknowledged_not_processed`, `test_frame_callback_refuses_excluded_camera_without_evidence`, `test_apply_masks_zeroes_exact_normalized_region`, `test_private_masks_zero_pixels_in_derived_evidence_before_hashing`, `test_retention_setting_updates_existing_and_new_artifacts_without_breaking_chain`, `test_shortened_retention_deletes_due_bytes_immediately_and_never_resurrects`, `test_provider_disconnect_cancels_work_and_never_auto_reconnects`, `test_household_deletion_requires_confirmation_and_is_household_scoped`) and Moto tests in `apps/mcp-orchestrator/tests/test_aws_runtime.py` (`test_household_deletion_erases_only_that_households_cloud_objects`, `test_failed_cloud_erase_blocks_republish_and_retries`). These are local/synthetic and emulated-cloud tests. No real Ring camera, Bee account or AWS deployment has exercised them.

Ring webhooks verify documented raw-body HMAC signatures before parsing and enforce server-side account/device bindings. Durable receipt IDs accept legitimate delayed retries without processing duplicates. A signed motion notification is not visual evidence. The WHEP receiver validates upstream session hosts, video capability and bounded session duration; decoder/model failures pause proof. Only authorized server-derived frames can drive live pose completion. The SHA-pinned model and per-rep frame hashes establish processing provenance, not medical accuracy or person identity.

Reports end at a private export or isolated synthetic receiver. Exact manifest, destination and deliberate owner confirmation are required for the demo dispatch. An MCP boolean cannot authorize official dispatch. No official police adapter, unsupported native haptic delivery or cross-app TV locking capability is claimed.

Security/negative tests cover cross-household media, forged webhooks, account/device scope, authenticated encryption context, evidence tampering, missing keys, expired evidence, consent, retries, stale revisions, count setters, repeated video/pose frames and storage failure. These are implementation tests; independent security review and production certification remain outstanding.
